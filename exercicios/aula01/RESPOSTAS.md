## Parte B
**B1**

*Causa: Requisitos incompletos ou mal entendidos*
- Como ela se manifestaria no Rota Escolar: 
O sistema poderia ser feito de uma forma diferente do que a secretaria realmente precisa. Por exemplo, alguma informação importante sobre a rota poderia ficar de fora.
- Contramedida: 
Conversar com as pessoas que vão usar o sistema antes de começar e anotar tudo o que elas precisam. Depois, confirmar com elas se os requesitos estão corretos.
- Como saber se a contramedida está funcionando: 
Os usuários devem confirmar se os requesitos estão certos antes do desenvolvimento começar. Se aparecer alguma mudança ou erro, deve ser anotado e analisado para ser corrigido.

*Causa: Falta de envolvimento do usuário*
- Como ela se manifestaria no Rota Escolar:
A equipe poderia criar funções que não ajudam muito no dia a dia porque não conversou com as pessoas que realmente vão usar o sistema.
- Contramedida:
Fazer uma reunião semanal de 30 minutos com a pessoa responsável pelas rotas escolares para saber se o sistema está sendo desenvolvido de acordo com o que ela precisa.
- Como saber se a contramedida está funcionando:
As reuniões devem acontecer toda semana e as decisões devem ser anotadas. Os usuários também devem testar e aprovar as funções antes delas serem finalizadas.

*Causa: Escopo crescente sem controle*
- Como ela se manifestaria no Rota Escolar:
Durante o projeto, poderiam aparecer vários pedidos de novas funções, como novos relatórios ou notificações, fazendo o projeto ficar maior e demorar mais.
- Contramedida:
Criar uma lista para registrar todos os novos pedidos e analisar cada um antes de decidir se ele vai entrar no projeto.
- Como saber se a contramedida está funcionando:
Todo novo pedido deve ser registrado e analisado antes de ser desenvolvido. Assim, fica mais fácil controlar o prazo e o que realmente faz parte do projeto.

*Causa: Ausência de gerenciamento de riscos*
- Como ela se manisfestaria no Rota Escolar:
Alguns problemas que poderiam ser previstos, como dados errados dos alunos ou atraso no recebimento de informações, poderiam acabar atrapalhando o andamento do projeto.
- Contramedida:
Fazer uma lista dos possíveis problemas do projeto e colocar para cada um deles o impacto, a chance de acontecer e o que pode ser feito para evitar ou resolver.
- Como saber se a contramedida está funcionando:
A lista deve ser revisada durante o projeto e os riscos mais importantes devem ter alguém responsável por acompanhar cada um deles.

**B2**

Mesmo que a maioria dos problemas de um projeto não seja técnica, isso não significa que UML, arquitetura e padrões de projeto não sejam importantes. Esses conhecimentos ajudam a organizar melhor o sistema e facilitam sua manutenção. Um projeto pode ter uma equipe bem organizada, mas ainda assim criar um sistema difícil de entender ou modificar. A UML ajuda a mostrar de forma mais clara como o sistema vai funcionar. A arquitetura ajuda a organizar as partes do sistema. Já os padrões de projeto ajudam a encontrar soluções para problemas que aparecem com frequência. Essas técnicas não resolvem problemas de comunicação ou de gestão. Porém, elas ajudam a evitar vários problemas no próprio software. Também tornam mais fácil fazer alterações no sistema no futuro. Por isso, um bom projeto precisa tanto de organização quanto de conhecimento técnico. Não adianta ter uma boa equipe se o sistema for mal construído. Da mesma forma, não adianta ter um sistema bem feito se o projeto for mal administrado. Por isso, as duas partes são importantes para a engenharia de software.

- De quem viria a informação definir o número?
Das servidoras da secretaria, por meio de testes de uso. Elas ajudariam a definir qual porcentagem seria adequada.

b) 
- Formulação mensurável:
Os relatórios devem ser gerados em até X segundos.
- De que viria a informação para definir o número?
Das servidoras que utilizam os relatórios, pois elas podem informar quanto tempo seria aceitável para o trabalho delas.

c) 
- Formulação mensurável:
O sistema deve ficar disponível durante X% do período de funcionamento, sem perder os dados cadastrados.
- De que viria a informação para definir o número?
Da secretaria e dos responsáveis pelo sistema, que devem informar quanto de disponibilidade é necessário para o trabalho não ser prejudicado.

d)
- Formulação mensurável:
As principais funções do sistema devem funcionar em X% dos testes realizados na zona rural.
- De que viria a informação para definir o número?
Das servidoras e usuários da zona rural, que podem ajudar a definir uma porcentagem adequada considerando as condições de internet e de uso.

**C2**

Se o objetivo continuasse apenas como “o sistema deve ser fácil de usar pelas servidoras da secretaria”, seria difícil saber no final se ele realmente foi alcançado. A equipe de desenvolvimento poderia dizer que o sistema ficou fácil de usar, enquanto as servidoras poderiam discordar e dizer que algumas funções são difíceis ou que precisam de ajuda. A equipe poderia se basear na própria experiência, e as servidoras, na experiência delas usando o sistema no dia a dia. Como não teria sido definido antes o que significa “fácil de usar”, não existiria uma forma objetiva de decidir quem está certo. Para resolver a discussão, seria necessário conversar com as servidoras e definir uma forma de medir esse resultado, como um teste de uso. Isso poderia acabar gerando mudanças no sistema e até atrasar o projeto. Por isso, o ideal seria definir essa medida antes do fim do projeto, consultando as pessoas que realmente vão usar o sistema.

## Parte D
**D1**

A) Apareceu trabalho novo 
Resposta da gestão:
A equipe descobriu uma situação que não estava prevista: os endereços estão em fichas de papel. A gestão deve avaliar quanto esse trabalho vai acrescentar ao projeto e atualizar o prazo, se for necessário.

B) A estimativa estava errada
Resposta da gestão:
O trabalho já era conhecido, mas a equipe calculou menos tempo do que realmente precisava. Nesse caso, é preciso rever o prazo e fazer uma nova estimativa mais realista.

C) Depende do que já se sabia antes. Se ninguém sabia que a servidora ficaria de férias, pode ser considerado uma situação nova. Se as férias já estavam marcadas e a equipe sabia disso, mas não colocou no planejamento, então a estimativa estava errada.
Resposta da gestão:
A gestão precisa verificar o que a equipe sabia quando fez o planejamento e, a partir disso, decidir se deve alterar o prazo ou corrigir a estimativa.

**D2**

Contratar mais pessoas pode parecer uma solução rápida para recuperar o atraso, mas pode acabar deixando o projeto ainda mais lento.
Primeiro, as pessoas novas precisam entender o projeto e aprender o que já foi feito. Para isso, a equipe que já está trabalhando terá que parar algumas tarefas para explicar tudo, o que pode diminuir o ritmo do trabalho.
Outro problema é que, com mais pessoas, também aumenta a necessidade de comunicação. A equipe vai precisar dividir as tarefas, explicar decisões e acompanhar o que cada pessoa está fazendo. Isso pode gerar mais reuniões, dúvidas e até erros.
Também pode acontecer de algumas tarefas não poderem ser divididas entre várias pessoas. Se uma tarefa depende do conhecimento de alguém que já está no projeto, colocar mais pessoas não vai fazer essa tarefa terminar mais rápido.
Por isso, antes de contratar mais pessoas, a gestão deveria entender por que o projeto está atrasado. Se o problema realmente for falta de pessoas para realizar tarefas que podem ser divididas, a contratação pode ajudar. Mas, se o problema for uma estimativa errada ou uma tarefa que depende de poucas pessoas, contratar mais gente pode piorar o atraso.

## Parte F
O caso escolhido é o Projeto Siafi XXI, que tinha como objetivo substituir o sistema Siafi, utilizado pelo Governo Federal.
O projeto começou no final dos anos 1990 e a previsão era que fosse implantado em janeiro de 2005.
Segundo o TCU, depois de mais de três anos de contrato, nenhum produto havia sido entregue e mais de R$ 30 milhões já tinham sido gastos.
O projeto acabou sendo encerrado em 2004, e depois foram feitos novos estudos para desenvolver o chamado Novo Siafi.
Entre os problemas encontrados estavam falhas no planejamento e no acompanhamento do projeto.
Também houve demora para perceber que o projeto não estava avançando como deveria.
Entre as causas estudadas na aula, podemos relacionar o caso com planejamento inadequado, problemas nas estimativas e no cronograma e falhas de gestão e acompanhamento.
Também houve problemas relacionados ao controle das entregas, já que nenhum produto tinha sido entregue no período analisado.
O caso mostra que um projeto pode consumir bastante tempo e dinheiro sem necessariamente chegar ao resultado esperado.
As principais informações foram retiradas do Acórdão 2673/2010 do Tribunal de Contas da União (TCU), que analisou o caso do Siafi XXI.
